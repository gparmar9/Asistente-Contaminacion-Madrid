Decisiones clave (novedades vs v2)

Base de datos Cambio
PostgreSQL en Docker con volumen nombrado (antes se planteaba SQLite). Mismo docker-compose.yml sirve en local ahora y en la nube después.
Modelo de anomalías Cambio
Isolation Forest por contaminante + baseline z-score (implementado y en producción local). El LSTM Autoencoder pasa a ser el siguiente paso (comparativa), no el punto de partida.
Datos
6 magnitudes objetivo (NO, NO2, NOx, O3, PM10, PM2.5). Histórico 2018–2026. API en tiempo real.
Ingesta Cambio
Pipeline a Postgres (pipeline_tiempo_real.py). El GitHub Action de CSV se mantiene como backup gratuito de datos crudos, separado del pipeline.
Scheduler Nuevo
GitHub Actions no puede escribir en un Postgres de Docker local (redes distintas). El pipeline corre en local (manual / tarea programada / servicio en compose) y en la nube cuando se despliegue.
CI/CD Nuevo
GitHub Actions con dos jobs: tests unitarios (sin DB) y tests de integración contra un Postgres de servicio efímero.
Protección de ramas Nuevo
Los merges a main solo pueden venir de development (workflow proteger_main.yml + branch protection).
LLM / Vector DB / Interfaz
Sin cambios respecto a v2: LLM local (Llama/Mistral) en Azure/AWS, ChromaDB solo para documentos externos, dashboard web con chatbot.

Estrategia implementada

  1. Baseline: valor esperado por (estación, magnitud, bloque, mes) → Z_SCORE. Materializado en baseline_historico.
  2. Modelo principal: Isolation Forest por contaminante sobre features comparables entre estaciones (Z_SCORE, COBERTURA, CV). Un modelo por magnitud, guardados en models/isolation_forest.joblib.
  3. Resultados: escribe anomaly_score, is_anomaly y expected_value en resumen_datos_ml.
  4. Tiempo real: el pipeline aplica el modelo a los datos entrantes y actualiza la tabla (upsert idempotente).
Validado sobre datos reales: el detector marca picos conocidos (p. ej. el pico de PM10 en Nochevieja por pirotecnia) y las caídas/congelaciones de sensor que el z-score por sí solo no ve.

Herramientas: Python + scikit-learn (Isolation Forest). PyTorch para el LSTM (siguiente).

Modelo de datos (PostgreSQL)

1. calidad_aire_horas_live — horario crudo

Mediciones hora a hora en formato largo. Clave única (estacion, magnitud, fecha), inserción con ON CONFLICT DO NOTHING.

2. resumen_datos_ml — tabla principal (la que consulta el chatbot)

Una fila por (estación, magnitud, día, bloque) con estadísticos, baseline y salida del modelo. ~1,27M filas para el histórico.

resumen_datos_ml -- identificación
├── estacion, magnitud, contaminante, fecha, bloque, hora_inicio, hora_fin
│ -- calendario
├── ano, mes, dia_semana, es_fin_semana
│ -- estadísticos del bloque
├── n_horas, cobertura, media, maximo, hora_maximo, minimo, hora_minimo, std, rango
│ -- baseline histórico
├── media_esperada, std_esperada, desviacion, z_score
│ -- salida del modelo ML
└── expected_value REAL, anomaly_score REAL, is_anomaly BOOLEAN

3. baseline_historico — valor esperado

Lookup de media_esperada / std_esperada por (estación, magnitud, bloque, mes). Lo usa la inferencia en tiempo real.

Infraestructura y CI/CD

Base de datos

  • PostgreSQL 18 en Docker (docker-compose.yml) con volumen nombrado: los datos persisten aunque se recree el contenedor.
  • En local ahora; el mismo compose se despliega en Azure/AWS del máster cuando toque (portable sin cambios).

GitHub Actions

  • Tests (tests.yml): job unit (lógica pura, sin DB) + job integración (Postgres de servicio efímero).
  • Backup CSV (ingesta_diaria.yml): cron que guarda los datos crudos diarios en un CSV versionado (red de seguridad gratuita).
  • Protección de main (proteger_main.yml): bloquea cualquier PR a main que no venga de development.
Nota de arquitectura: GitHub Actions corre en la nube y no llega a un Postgres de Docker local. Por eso la ingesta a la base de datos se ejecuta donde vive la DB (local ahora, cloud después), no en el Action.
