Componente 1: Deteccion de Anomalias (ML)

Enfoques evaluados

OpcionProsContrasVeredicto
Isolation Forest / LOF Simple, rapido, buen baseline Sin conciencia temporal Buen baseline
LSTM Autoencoder Aprende patrones temporales, detecta anomalias complejas Necesita mas datos/ajuste Mejor opcion para TFM
Prophet + analisis de residuos Facil de implementar, maneja estacionalidad Menos flexible Buena alternativa
Estadistico (Z-score, IQR) Trivial de implementar Demasiado ingenuo para datos multi-estacion Solo como complemento

Estrategia

  1. Baseline: Umbrales estadisticos por estacion/magnitud (Z-score en ventanas moviles)
  2. Modelo principal: LSTM Autoencoder entrenado en CalidadAireHoras — aprende patrones "normales" por estacion+magnitud, marca errores de reconstruccion como anomalias
  3. Resultados: El modelo escribe anomaly_score, is_anomaly y expected_value en la tabla ResumenDatosML
  4. Tiempo real: Desplegar el modelo sobre datos entrantes, marcar anomalias → alertas

Herramientas: Python + PyTorch o TensorFlow, scikit-learn para baselines

Modelo de Datos

Tabla principal: CalidadAireHoras (~11M filas)

Datos brutos hora a hora. El LLM puede consultarla para detalle exacto si es necesario.

Tabla resumen: ResumenDatosML

Agregacion por bloques del dia. Es la tabla principal que consulta el LLM.

ResumenDatosML
├── ESTACION         INTEGER
├── MAGNITUD         INTEGER
├── FECHA            DATE
├── BLOQUE           TEXT     -- madrugada / manana / tarde / noche
├── HORA_INICIO      INTEGER   -- 0, 7, 13, 20
├── HORA_FIN         INTEGER   -- 6, 12, 19, 23
├── MEDIA            REAL
├── MAXIMO           REAL
├── HORA_MAXIMO      INTEGER
├── MINIMO           REAL
├── HORA_MINIMO      INTEGER
├── ANOMALY_SCORE    REAL     -- del modelo ML
├── IS_ANOMALY       BOOLEAN   -- flag binario
└── EXPECTED_VALUE   REAL     -- valor que el modelo esperaba

Bloques horarios

BloqueHorasRelevancia
Madrugada00:00 – 06:00Baja actividad, contaminacion baseline
Manana07:00 – 12:00Hora punta, picos de NO2
Tarde13:00 – 19:00Picos de O3 (sol + calor), actividad al aire libre
Noche20:00 – 23:00Trafico vespertino, enfriamiento

~24 estaciones × 18 magnitudes × 2.920 dias × 4 bloques = ~5M filas. El LLM puede agregar bloques para obtener datos diarios si es necesario.

Componente 3: Vector DB — Solo documentos externos

Cambio clave: La Vector DB no almacena datos de contaminacion. Solo contiene documentos que aportan conocimiento que no esta en los datos: efectos en salud, normativa, guias, estudios.

Que se almacena en la Vector DB

  • Estudios de salud: efectos de contaminantes en poblaciones vulnerables (asmaticos, ninos, ancianos)
  • Normativa: limites OMS, directiva UE de calidad del aire, legislacion espanola (BOE)
  • Guias clinicas: recomendaciones de actuacion segun niveles de contaminacion
  • Estudios de alergias: relacion entre contaminantes y reacciones alergicas
  • Contexto local de Madrid: fuentes de contaminacion, patrones estacionales conocidos, zonas especificas

Componente 4: Informes Automaticos

Logica de generacion

  1. Comprobar anomalias: Consultar ResumenDatosML del dia — hay registros con IS_ANOMALY = true?
  2. Si hay anomalias: Enviar al LLM un prompt pidiendo que explique las anomalias detectadas, usando los tools (SQL para datos, Vector DB para contexto de salud)
  3. Si no hay anomalias: Seleccionar un prompt aleatorio de un conjunto rotativo de preguntas predefinidas (ej: "Compara el O3 de esta semana con la misma semana del ano pasado", "Cual es la estacion con mejor calidad del aire hoy?")
  4. Publicar: El informe generado aparece en el web dashboard

Orden de Implementacion

Fase 1: Datos y modelo ML

  1. Tablas de lookup: Magnitudes (hecho), Estaciones (pendiente: nombres, ubicaciones, zonas)
  2. Crear ResumenDatosML: SQL de agregacion desde CalidadAireHoras con los 4 bloques horarios
  3. Baseline estadistico: Z-score por estacion+magnitud en ventanas moviles
  4. LSTM Autoencoder: entrenar, evaluar, escribir anomaly_score/is_anomaly/expected_value en ResumenDatosML
  5. Ingesta en tiempo real: job programado para API de Madrid → SQLite → inferencia ML

Fase 2: Vector DB + documentos

  1. Recopilar documentos: estudios de salud, normativa, guias (ver seccion TODO)
  2. Pipeline de embeddings: chunking + sentence-transformers → ChromaDB
  3. Validar retrieval: probar preguntas ejemplo y verificar que los chunks devueltos son relevantes

Fase 3: LLM + tool use

  1. Desplegar LLM local: Ollama/vLLM en Azure/AWS con GPU
  2. Implementar tools: query_sql (read-only) + search_documents (ChromaDB)
  3. System prompt: contexto de dominio en espanol, disclaimer de salud, instrucciones de tools
  4. Probar chatbot: preguntas variadas, verificar calidad de respuestas

Fase 4: Informes + dashboard

  1. Logica de informes: deteccion de anomalias → prompt al LLM, o prompt rotativo si no hay anomalias
  2. Definir prompts rotativos: conjunto de preguntas variadas para dias sin anomalias
  3. Web dashboard: interfaz con informes + chatbot integrado

Verificacion

  • LLM usa tools correctamente: SQL para datos, Vector DB para contexto de salud
  • Informes automaticos se generan con anomalias reales o prompts rotativos
  • Chatbot responde coherentemente en espanol con disclaimer visible
