02

Un turno hoy, paso a paso

Cada llamada al modelo responde una sola pregunta y tiene un valor por defecto si falla. Entre llamada y llamada, el código puede vetar, forzar o cerrar el turno sin preguntar al modelo.

Lo hace el LLM Lo hace el código Lo hace el servicio RAG
  1. 1

    Sesión y memoria

    Código

    Llega {pregunta, session_id}. Un turno a la vez por sesión: si ya hay uno en marcha, el segundo espera (evento en_espera). Se carga la ventana de historial: turnos completos que quepan en 1.500 tokens estimados.

    Memoria en el proceso: 20 turnos por sesión, se olvida tras una semana sin actividad y se pierde al reiniciar. Al modelo solo llega texto limpio; el historial ayuda a entender la pregunta, nunca cuenta como fuente.

  2. 2

    Clasificar la intención

    LLM

    Una llamada corta a temperatura 0 con 10 s de límite. Devuelve dos líneas, intencion: y tema: (salud, normativa, proyecto o ninguno). El parser es estricto: cualquier desviación, fallo o timeout da DESCONOCIDA.

  3. 3

    Decidir qué herramientas se ofrecen

    Código
    DOCUMENTALSolo se ofrece buscar_evidencias. Si el RAG está caído, frase fija.Sigue al paso 4
    DESCONOCIDATodas las herramientas, ninguna obligada. Un clasificador caído no quita capacidades.Sigue al paso 4
    CHARLAEl modelo responde sin herramientas, con un prompt corto. Sale en tokens.Fin
    DATOSFrase fija: el agente aún no consulta mediciones.Fin, sin modelo
    PREDICCIONFrase fija: el sistema no hace predicciones; ofrece lo documental.Fin, sin modelo
    FUERA_DE_ALCANCEFrase fija de rechazo (restaurantes, fútbol, polen, ruido…).Fin, sin modelo
  4. 4

    Bucle de herramientas

    LLMCódigo

    El modelo pide herramientas y el código las ejecuta, como mucho 3 vueltas. Las herramientas nunca lanzan excepciones: devuelven {ok, datos | error} y el modelo puede corregirse en la vuelta siguiente.

    Herramienta vetada → error al modelo, no se ejecuta Búsqueda vacía → frase fija sin_evidencia DOCUMENTAL sin buscar → busca el código RAG sin servicio → frase fija, sin repetir 3 vueltas agotadas → síntesis forzada sin herramientas
  5. 5

    Buscar evidencias

    RAG

    POST /rag/evidencias devuelve fragmentos bajo el umbral de distancia (0,1754). El agente los renumera D1..Dn sin repetir chunk_id, y al modelo solo le llega el texto: nunca los identificadores internos.

    La definición de la herramienta la publica el propio RAG (GET /rag/herramienta). Si no responde, la herramienta no se ofrece en ese turno.

  6. 6

    Síntesis documental

    LLM

    Llamada aparte, sin herramientas y con mensajes nuevos (pregunta + evidencias). El modelo devuelve un JSON: {estado, afirmaciones[{texto, evidencias:[Dn]}], limitaciones}. Su texto libre del bucle se descarta.

  7. 7

    Validar y entregar tal cual

    RAG

    POST /rag/validar comprueba que cada Dn existe y renderiza el texto final con las citas, el aviso sanitario y la bibliografía. Si no valida, una reparación con el mensaje del RAG; si vuelve a fallar, frase de insuficiencia. El agente entrega ese texto sin tocarlo.

  8. 8

    Comprobar y guardar

    Código

    Tres reglas sobre lo que escribió el modelo: cifras que no salen de las evidencias citadas, fuga del prompt (10 palabras seguidas en común) e internos (nombres de herramientas, chunk_id). Hoy solo observan; cada una podrá bloquear cuando demuestre 0 falsos positivos.

    Se guarda el turno con sus metadatos. Al contexto del turno siguiente van las afirmaciones sin marcas [Dn], porque esas marcas solo valen dentro de su turno.

RutaLlamadas al LLMQué recibe el cliente por SSE
Frase fija (DATOS, PREDICCION, fuera de alcance)1status → passthrough → done
Charla2status → token × n → done
Documental4 (5 con reparación, 3 si busca el código)status por fase mientras espera → passthrough → done
clasificando→redactando→buscando→redactando→validando→passthrough→done

La ruta documental no se emite en tokens: un JSON a medias no se puede validar. Mientras tanto el cliente recibe la fase en curso, repetida cada 0,7 s como latido.

03

Así se ve un turno en las trazas

Cada paso del turno es un span OpenTelemetry con atributos OpenInference. El mismo árbol va a Phoenix (cascada interactiva, autoalojado en un contenedor) y a un JSONL del que sale nuestro informe de latencia, tokens y coste.

La cascada de esa captura

Casi todo el tiempo es del modelo. La búsqueda y la validación juntas no llegan a 0,25 s.

Esta misma vista destapó un fallo que los tests no cubrían: con el RAG caído, el turno esperaba dos timeouts seguidos (43 s) antes de la frase fija.

04

Decisiones que marcan el diseño

Lo que se eligió, lo que se descartó y por qué. El registro completo tiene más de 70 decisiones fechadas.

Bucle de herramientas escrito a mano

DescartadoReAct o AgentWorkflow de LlamaIndex, LangGraph

Por quéEsos frameworks esconden justo el bucle que queremos controlar. El nuestro cabe en un fichero y cada fase le añade un paso visible.

LlamaIndex solo como cliente del LLM

DescartadoSDKs directos (openai + boto3), LangChain, LiteLLM

Por quéUna interfaz para OpenAI-compatible y Bedrock Converse: traduce los dos formatos de tool use y el streaming. Si hubiera que quitarlo, cambian tres ficheros.

Clasificador + tabla de decisión en código

DescartadoUn prompt de sistema con reglas y que el modelo decida todo

Por quéLas preguntas de datos, predicción y fuera de alcance se resuelven con 1 llamada y sin riesgo de que el modelo improvise.

El texto con citas lo escribe el RAG

DescartadoQue el agente o el modelo compongan la respuesta final

Por quéA un LLM no se le pide que cite bien: se le comprueba. El modelo solo elige IDs; título, sección y bibliografía salen del corpus.

Síntesis con mensajes nuevos, sin herramientas

DescartadoReutilizar la conversación del bucle

Por quéBedrock Converse rechaza bloques de herramienta sin toolConfig. Además, el prompt queda más corto.

Memoria en el proceso, también en producción

DescartadoPostgresChatStore, Redis, SimpleChatStore

Por quéEs un TFM con un solo proceso. Detrás de una interfaz: pasar a base de datos cambiaría una clase.

Phoenix + JSONL propio

DescartadoLangfuse, Opik (Postgres + ClickHouse + Redis), SaaS como LangSmith, CloudWatch

Por quéUn contenedor sin dependencias. El JSONL hace que el informe no dependa de que Phoenix esté levantado.

Evaluación sin jueces LLM

DescartadoUn juez LLM con MLflow o Phoenix Evals; una nota única

Por quéTres criterios separados (JSON válido, referencias válidas, respuesta correcta leída por una persona) dicen dónde falla un modelo.

Comprobaciones en observación primero

DescartadoBloquear desde el principio; un interruptor global

Por quéUna regla ruidosa no debe impedir bloquear con las fiables. Cada regla bloquea por separado cuando tenga 0 falsos positivos.

Elección de modelo aplazada

DescartadoElegir ya con el lote de 12 casos

Por quéHoy solo medimos clasificación, documentación y charla. Las herramientas de datos pueden pedir otro tipo de modelo.

05

Aprendizajes para compartir

Dos fallos que parecían del modelo y no lo eran. Probablemente os ahorren tiempo a vosotros.

4/20 → 20/20

Mira las respuestas crudas antes de juzgar al modelo

Ministral sacó un 4/20 en el clasificador. Las 16 «malas» eran correctas pero en negrita (**DOCUMENTAL**) y el parser las rechazaba. Una línea en el prompt lo arregló. Mide el formato y la comprensión por separado.

512 → 2048 tokens

Un modelo que razona gasta en pensar tus tokens de salida

gpt-oss cortaba el JSON en un punto distinto cada vez: 4 de 18 respuestas acabaron en insuficiencia. Parecía que no sabía hacer JSON; se quedaba sin espacio. Fija siempre max_tokens.

06

Pendiente

Lo que queda abierto antes de dar el agente por cerrado. Lo marcado como «revisión humana» no lo puede hacer un script: hay que leer las respuestas.

Evaluación de los modelos

  • Puntuar las respuestas de los lotesrevisión humana

    Rellenar la columna «Correcta» (sí, no o parcial) de los ficheros turnos_*.md en Agente/evaluacion/resultados/: lote de 12 casos, conversaciones de la fase 5 y casos adversarios, con los dos modelos. Hoy solo hay métricas automáticas (ruta, JSON, citas); sin esta puntuación no se puede valorar la calidad del contenido ni del español.

  • Revisar los hallazgos de las comprobacionesrevisión humana

    Marcar cada hallazgo de comprobaciones_fase6_20261006.md como acierto o falso positivo. Con eso se decide qué reglas pasan a bloquear: la de cifras necesita antes ignorar «2.5 micras», y la de fuga solo detecta 1 de 4 fugas reales.

  • Confirmar el clasificador con preguntas nuevas

    El 29/29 se logró ajustando el prompt sobre las mismas preguntas. Falta un juego de casos que no se haya usado para ajustarlo, y revisar algunas etiquetas discutibles del guion.

  • Elegir modelotras SQL y ML

    Cuando existan las herramientas de datos y del detector, repetir los lotes con los dos modelos y decidir con esas cifras y con la puntuación humana.

Despliegue (fase 7)

  • Dockerizar el agente

    El Dockerfile existe, pero la imagen jupiter-agente no se ha construido. Falta añadir el servicio agente (puerto 8200) al docker-compose junto al orquestador, apuntar ApiUsuario con AGENTE_URL y añadir la opción al workflow de despliegue.

  • Credenciales de Bedrock por IAMpropuesta sin decidir

    Ninguna clave en la imagen, en .env ni en el compose. En la EC2, el rol de la instancia con permiso bedrock:InvokeModel e InvokeModelWithResponseStream; el contenedor llega a esas credenciales por el servicio de metadatos (IMDSv2 con límite de saltos 2). En local, las claves temporales del perfil SSO pasadas como variables de entorno al levantar el compose.

  • Un solo proceso

    La memoria y el bloqueo por sesión viven en el proceso: el agente debe desplegarse con un único proceso, y las conversaciones se pierden en cada despliegue.

Comprobaciones de punta a punta

  • Probar la memoria por HTTP

    La cadena NO2 → «¿Y en niños?» → «¿Y a largo plazo?» se ha probado en los lotes, pero no a través de ApiUsuario /chat/stream, ni con una sesión nueva o tras reiniciar el agente.

  • Turnos cancelados en el informe

    El informe de trazas los cuenta como errores; deberían salir como cancelados.

Preguntas abiertas

  • ¿Consultas predefinidas (como hace LLMOrchestrator con sus 5 consultas) o SQL generado por el modelo? Lo primero es más seguro; lo segundo, más flexible.
  • ¿Hace falta un modelo de razonamiento para elegir consulta y parámetros? Para la ruta documental no hizo falta.
  • Si en una misma respuesta el modelo pide una búsqueda vacía y una consulta SQL, hoy el turno se cierra como sin_evidencia. Habrá que cambiarlo.
08

Frente a LLMOrchestrator

El orquestador fue el primer agente (septiembre): un bucle con el SDK de OpenAI en el que el modelo decide todo guiado por un prompt de sistema con 8 reglas. El agente nuevo nació porque ese bucle no tenía puntos donde el código pudiera vetar, forzar o cerrar el turno; añadirlos equivalía a reescribirlo.
